# ResearchKB 第 7—14 天开发路线

制定日期：2026-09-28。默认每天约 2—4 小时；你愿意增加工作量时，可以把相邻两天合并，但必须完成当天验收再推进。第 1—6 天为已完成的学习阶段，第 7 天起按[新版项目总览](ResearchKB_新版项目总览.md)开发。

## 第 7 天：跨行业通用化与基线保护

**目的**：新的传统行业 PDF 可以走现有上传和问答主链，同时旧的 AI 基础设施样本继续可用。

**任务**：记录当前问答基线；将 `app.py`、`qa.py`、`vision_service.py` 中限定行业的产品文案和提示词改成通用表述；检查 `README.md` 和 `pyproject.toml` 的项目描述；将业务配置集中到一个小配置模块，但不要把每个常量都做成 UI 控件；用一份非 AI 行业、可提取文字的 PDF 做上传与引用问答验收。详细步骤见[明天任务](2026-09-29_第七天任务.md)。

**验收**：旧样本问答和拒答不回退；新 PDF 至少 1 个问题能引用正确页码；界面与模型提示词不再限定 AI 行业；清楚显示处理页数和截断状态。

## 第 8 天：文档登记簿

**目的**：让用户能看到“有哪些文档、属于哪个公司、处理是否成功”，不再从 Milvus 片段反推文档列表。

**任务**：设计 SQLite `documents` 表；保存唯一文件名、SHA-256、标题、行业、公司、Ticker、文档类型、报告日期、上传时间、处理页数和入库状态；把上传流程与登记簿连接。暂时只做单用户、一个文档属于一个研究项目，避免过早设计权限系统。

**验收**：同一文件重复上传不产生重复登记；同名不同内容能区分；解析或入库失败后状态可见；原有 5 份 PDF 可通过一次性迁移或重建登记进入目录，279 条 Milvus 证据不丢失。

## 第 9 天：研究项目、筛选和文档管理

**目的**：按项目、行业、公司和日期组织资料，支持删除及重新入库。

**任务**：增加轻量研究项目和文档筛选；用 SQLite 选择文档，再将文件名映射为 Milvus `source` 过滤；实现删除前显示涉及的文件、图片与向量数量，删除后同步更新三处；重新入库需考虑稳定 ID 和已存在证据；为数据迁移保留备份步骤。

**验收**：两个不同行业的项目互不串资料；删除一份演示文件后列表与检索同时消失；重复入库不重复计费。不要删除初始 5 份样本来做验收。

## 第 10 天：图表处理进入上传流程

**目的**：普通用户上传 PDF 后可自行选择图表页，而不必修改 `CHART_PAGES` 脚本。

**任务**：上传后预览页码，输入或选择少量页码；复用 `page_renderer.py`、`vision_service.py`、`visual_evidence.py`、`indexer.py`；页面展示每页处理状态与费用相关的调用次数；处理失败不应抹掉已成功的文本证据。

**验收**：对一份新 PDF 指定 1 页图表，问答可引用图像证据并显示原图；重复处理不增加实体；页码越界给出清楚错误。

## 第 11 天：接入第一种官方外部来源

**目的**：让研究不止依赖上传资料。先把范围收窄到美股公司的 SEC 披露目录和原始链接。

**任务**：输入 Ticker，解析公司标识，获取最近 10-K / 10-Q 的标题、报告期、提交日期及 SEC URL；用户选择后导入或打开原文；记录采集时间和处理状态。请求参数、频率限制和异常处理按当时 SEC 官方说明实现，不把抓取结果当成已验证的财务数字。

**验收**：至少两家公司能列出正确的官方披露；导入的资料显示原 URL 与日期；网络失败和无结果有可理解提示。传统行业美股同样可用。

## 第 12 天：资料库 / 综合研究两种模式

**目的**：明确区分本地材料与外部来源，并处理资料过时的问题。

**任务**：界面显式选择“仅资料库”或“综合研究”；外部证据与本地证据统一为带来源类型、URL / 页码、日期的结构；回答和引用区域分别标记来源；当不同年份数字冲突时让模型说明口径与时间。先复用已有问答代码，不引入 LangGraph。

**验收**：关闭联网时不会调用外部来源；开启后能分别引用本地页码和官方 URL；库外问题不会被本地无关片段硬答；旧数字和新数字不被混写。

## 第 13 天：公司对比与研究简报

**目的**：从“问一个问题”升级为可保存、可复查的研究成果。

**任务**：先做固定而实用的 Markdown 模板：研究问题、核心结论、关键事实、公司 / 行业对比、催化因素、风险、信息缺口、来源清单；用户选择资料范围和报告日期；导出 `.md`。若加入财务比率，先由 Python 根据明确来源与单位计算，再让模型解释。

**验收**：一份双公司简报能追溯每个关键数字的来源；缺失数据明确写“未找到”；再次生成不会覆盖用户旧文件。

## 第 14 天：质量评测和交付

**目的**：用结果说明系统适合什么场景、有哪些边界。

**任务**：建立约 20 个覆盖 AI 与传统行业、图表、库外问题、不同年份和来源冲突的固定问题；记录检索命中、引用有效性、拒答、耗时与模型调用次数；比较是否需要 BM25 或重排，只有确有收益才加；更新 README、启动说明、演示路径和架构图。

**验收**：另一位同学可以按 README 启动；能演示上传→检索→官方来源→简报；能指出至少一个失败案例及原因；GitHub 提交不含 `.env`、PDF 原件和私有图片。

## 每日代码交付格式

1. 本段代码解决的问题与所在文件。
2. 代码依赖的已有模块、输入、输出和调用者。
3. 适合在 PyCharm 亲手输入的分段代码，含关键中文注释与函数 docstring；第三方包函数和难懂变量单独解释。
4. 一条运行或验收命令、预期输出和实际结果记录位置。
5. 当天复盘中的文件关系图与下一天的衔接。

每天完成并检查 `git diff` 后再提交；开发路线文档本身不会替代当日实际复盘。
